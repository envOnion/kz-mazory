# AGENTS.md — монорепозиторий Mazory

В Docker Compose работают следующие сервисы:

```text
Docker Compose:
  frontend :5173  → Vue 3 + TypeScript + Vite + Tailwind CSS
  backend  :8000  → Django 6.1 (DRF) + SimpleJWT (/api/*, /admin/*)
  qcluster        → Django Q2 Worker (фоновые задачи через Redis)
  redis    :6379  → Брокер очередей Django Q2 и кэш
  waha     :3000  → WhatsApp HTTP API (Noweb engine)
```

- **Backend** (`backend/`) на Django 6.1 и Django REST Framework предоставляет весь API:
  аутентификация по телефону и OTP, интеграция с WhatsApp через WAHA, аналитический дашборд KPI,
  обработка AI-запросов (`/api/chat/query/`), административная панель Django (`/admin/`) и фоновые задачи через Django Q2.
- **Frontend** (`frontend/`) построен на Vue 3 (Composition API), Vite, TypeScript и Tailwind CSS.
- **QCluster** (`qcluster`) выполняет асинхронную обработку очередей (отправка OTP, взаимодействие с WAHA, долгие аналитические операции).
- **WAHA** (`waha`) шлюз WhatsApp Web/Noweb API для приема и отправки сообщений.

## Процесс работы над задачей

Каждая задача выполняется в следующем порядке:

1. **Сначала синхронизировать ветки.** До создания задачи, спецификации или
   начала реализации выполнить `git pull origin main`. Ветка `main` используется
   только для синхронизации: запрещено коммитить или отправлять изменения
   непосредственно в неё. Вся работа продолжается в отдельной ветке задачи.
2. **Определить идентификатор задачи.** Проект ведется на GitHub, без использования
   Bitrix и GitLab. Если задача привязана к GitHub Issue, запросить у пользователя
   номер или ссылку на issue (например, `issue-42` или `#42`). Если пользователь ставит
   задачу напрямую или она не связана с GitHub Issue, использовать короткий slug
   на английском языке без запроса ссылки (например, `whatsapp-otp`, `kpi-chart`, `auth-flow`).
3. **Создать ветку задачи.** Работать только в отдельной ветке
   `<type>/<task-id-or-slug>`, где `<type>` — одно из значений `bugfix`,
   `feature`, `refactor`, `docs` или `chore`.
4. **Создать спецификацию.** До изменения кода создать единственный артефакт
   задачи в `specs/`. Файл называется
   `task_YYYY-MM-DD_HH-mm-ss_MSK.md`: дата и время фиксируются в момент создания
   по московскому времени (MSK, UTC+3). Порядок компонентов имени обязателен,
   чтобы список спецификаций сортировался хронологически. Спецификация содержит
   постановку, требования, планируемые изменения и критерии готовности.
   Если задача затрагивает модели Django или структуру БД, в начале спецификации
   обязательна Mermaid ERD; для крупной задачи также обязательна Mermaid sequence-диаграмма.
   Подробные требования — в разделе «Спецификации задач».
5. **Согласовать спецификацию.** Реализация начинается только после review и
   подтверждения спецификации пользователем. Отдельный файл плана не создаётся.
7. **Создать и выполнить сквозные E2E тесты через Playwright.** E2E тесты через Playwright (`npm run test:e2e` в `frontend/e2e/`) **строго обязательны для создания с любой задачей**. Тесты выполняются на работающем приложении `http://localhost:5173`: проверяют реальный рендеринг UI в браузере, отправку запросов в чат, появление динамических виджетов и графиков, работу состояний загрузки и обработку ошибок. Также проверяется отработка фоновых задач (Django Q2, WAHA) через логи.
   Unit- и изолированные архитектурные тесты не заменяют E2E тесты; E2E тесты на Playwright являются обязательным стандартом верификации.
8. **Проверить.** Запустить проверки типов и сборку фронтенда, системную проверку
   Django и проверку отсутствия незафиксированных изменений схемы БД
   (`makemigrations --check`), запустить сервисы в Docker и просмотреть логи.
   См. разделы «Обязательные проверки перед коммитом» и «Локальный запуск».
9. **Исправить.** При сбое любой проверки устранить причину и повторить
   проверку.
10. **Создать PR.** После реализации и проверки автоматически создать Pull Request (PR)
    на GitHub. Целевой веткой всех PR должна быть **только** `main`. Запрещено
    создавать или перенаправлять PR задачи в другие ветки без прямого указания.
    Описание или комментарий PR должен включать ссылку или номер GitHub Issue (если есть),
    краткое описание изменений и список выполненных проверок.
11. **Объединить PR.** После прохождения проверок PR и обязательных этапов review
    объединить его. Не добавлять подпись о соавторстве Claude/Gemini/AI в коммиты или текст PR.

## Сквозные правила

- **Идентификаторы сущностей.** Соблюдать строгий контракт типов:
  - В Django ORM по умолчанию используются целочисленные идентификаторы (`id: int`, `BigAutoField`),
    если в конкретной модели явно не задан `UUIDField`.
  - На фронтенде строго соблюдать тип, объявленный в API: если ID числовой — использовать `number`,
    если UUID — `string`.
  - Запрещены объединения `number | string` и `string | number`, хаотичные приведения через
    `Number`, `parseInt`, `parseFloat` или унарный `+`, а также резервный выбор между разными полями
    идентификатора. Если контракт целочисленный — везде использовать `number`/`int`; если строковый —
    везде `string`/`str`.
- **Фоновые задачи и асинхронность (Django Q2 & WAHA):**
  - Все внешние вызовы (отправка сообщений через WAHA, отправка OTP, долгие запросы к LLM/ИИ, экспорт данных)
    **запрещено** выполнять синхронно в HTTP-обработчиках Django.
  - Они должны передаваться в очередь фоновых задач через `django_q.tasks.async_task`
    и обрабатываться воркером `qcluster`.
  - WAHA API вызывается только из фоновых задач `tasks.py`, с использованием настроек
    `settings.WAHA_API_URL` и `settings.WAHA_API_KEY`.
- **Аутентификация и безопасность:**
  - Аутентификация в Mazory реализована через JWT (`rest_framework_simplejwt`). Токен передается
    в заголовке `Authorization: Bearer <access_token>`.
  - Вход пользователей выполняется по номеру телефона и одноразовому 4-значному OTP-коду
    с защитой от спама через Redis-кулдаун (`COOLDOWN_TTL`) и ограничением попыток ввода (`MAX_ATTEMPTS`).
  - **Публичные эндпоинты без аутентификации (`AllowAny`):**
    `POST /api/auth/send-code/`, `POST /api/auth/verify-code/`, `POST /api/whatsapp/send/` (шлюз) и админка `/admin/`.
    Для всех остальных эндпоинтов бизнес-логики и аналитики обязателен класс `permission_classes = [IsAuthenticated]`.
- **Секреты и конфигурация:**
  - В коде Django секреты, ключи API и токены никогда не читаются напрямую через хардкод.
    Использовать `os.getenv` с дефолтными значениями для dev-окружения либо параметры из `django.conf.settings`.
- **Логирование и отладка:**
  - Использовать стандартный `logging.getLogger(__name__)`.
  - Для отладки в Docker Compose предусмотрены флаги `stdin_open: true` и `tty: true`.
    Для подключения к интерактивной консоли бэкенда при наличии `breakpoint()` использовать:
    `docker attach mazory-backend` (выход: `Ctrl + P`, затем `Ctrl + Q`).
- **Контракты API:**
  - DRF эндпоинты возвращают стандартные HTTP-коды состояния (200, 201, 400, 401, 403, 404, 429).
  - Не оборачивать ответы в самодельные конверты `{ success: true, data: ... }`, если клиент ожидает данные напрямую.
  - При ошибках валидации возвращать понятные сообщения (например, `{"error": "..."}`).
- **Фронтенд соглашения:**
  - Vue 3 с `<script setup lang="ts">`, TypeScript, Tailwind CSS, Lucide icons.
  - Запрещено использовать тип `any`. Все структуры данных и DTO типизируются в `frontend/src/types/`.
  - Все сетевые запросы к API формируются относительно `import.meta.env.VITE_API_URL`.

## Спецификации задач

- `specs/` — единственный обязательный каталог с текстовыми артефактами задач.
- Для каждой задачи создаётся ровно одна спецификация. Отдельные планы, отчёты,
  ADR, реестры, ER-диаграммы, runbook и постоянная проектная документация не
  создаются, если пользователь явно не запросил конкретный документ.
- Имя спецификации имеет формат `task_YYYY-MM-DD_HH-mm-ss_MSK.md`, где дата и
  время берутся в MSK (UTC+3). Имя не зависит от номера PR и после создания PR
  не меняется.
- **Задачи с БД:** если спецификация затрагивает схему БД, модели Django,
  миграции, запросы, чтение или запись данных, в начале спецификации — сразу
  после заголовка и метаданных, до постановки и требований — обязательна
  ER-диаграмма в блоке `mermaid` с типом `erDiagram`. Показать затронутые
  таблицы, значимые поля, первичные и внешние ключи, связи и их кратность.
  Существующую структуру проверять по актуальным моделям `models.py` и миграциям;
  планируемые изменения явно отличать от текущего состояния.
- **Крупные задачи:** обязательна диаграмма последовательности в блоке
  `mermaid` с типом `sequenceDiagram`. Крупной считать задачу, которая
  затрагивает несколько подсистем или меняет многошаговый сквозной процесс,
  включая асинхронные операции (Django Q2, WAHA) и внешние интеграции. Диаграмма должна
  показывать участников, порядок взаимодействий, значимые ветвления и ошибки
  основного сценария. Размещать её в начале спецификации, после ERD, если та
  требуется, и до постановки и требований.
- Если задача одновременно крупная и затрагивает БД, обязательны обе
  диаграммы. Они являются частью единственной спецификации в `specs/`,
  а не отдельными документами; обновлять их при изменении требований и плана.
- Изменения требований, плана реализации и критериев готовности вносятся в ту
  же спецификацию, а не в дополнительные Markdown-файлы.
- Для локального поиска использовать `rg`, для истории —
  `git log -- <path>` и `git blame <path>`.

## Обязательные проверки перед коммитом

Для любого изменения Backend (`backend/`) выполнить:

```bash
# Проверка конфигурации Django
uv run --project backend python manage.py check
# или внутри Docker:
docker compose exec backend python manage.py check

# Проверка отсутствия расхождений между моделями и схемой миграций
uv run --project backend python manage.py makemigrations --check
# или внутри Docker:
docker compose exec backend python manage.py makemigrations --check
```

**После каждой задачи обязательно проверить отсутствие незафиксированных миграций моделей.**
Команда `python manage.py makemigrations --check` должна завершаться с кодом 0 и сообщением `No changes detected`.
Если модели были изменены, необходимо создать миграцию (`python manage.py makemigrations`), применить её
(`python manage.py migrate`) и убедиться, что повторный check чист.

Для любого изменения Frontend (`frontend/`) выполнить:

```bash
cd frontend
npm run build
```

Команда `npm run build` выполняет проверку типов через `vue-tsc -b` и сборку Vite. Сборка должна проходить
без единой ошибки компиляции TypeScript.

**Обязательные сквозные Playwright E2E тесты:**
Для любой задачи, затрагивающей поведение или UI, обязателен прогон тестов через Playwright на работающем приложении `http://localhost:5173`:
```bash
cd frontend
npm run test:e2e
```
Все тесты в `frontend/e2e/*.spec.ts` должны завершаться с кодом 0 (зеленый статус). Тесты проверяют рендеринг компонентов, взаимодействие с чатом, монтирование виджетов и графиков Chart.js, корректность ответов бэкенда и отсутствие консольных ошибок.

Также проверить отработку воркера `qcluster` и WAHA через логи:
```bash
docker compose logs --tail=50 backend qcluster waha
```

Для изменений только документации (`.md`), инструкций или конфигурации инструментов,
которые не меняют поведение приложения, проверить diff; запуск приложения и сборка не требуются.
Обязательная проверка миграций моделей сохраняется.

## Локальный запуск

```bash
# Сборка и запуск всех сервисов в фоне
docker compose up -d

# Запуск с логами в реальном времени
docker compose up

# Пересборка конкретного сервиса при обновлении зависимостей или Dockerfile
docker compose up -d --build backend
docker compose up -d --build frontend
docker compose up -d --build qcluster

# Просмотр логов конкретного сервиса
docker compose logs -f backend
docker compose logs -f frontend
docker compose logs -f qcluster
docker compose logs -f waha
```
