# Удаляемые конфигурации ИИ и безопасное восстановление ошибочных сообщений

- Задача: `ai-config-error-recovery`; прямая постановка пользователя, без GitHub Issue.
- Ветка: `feature/ai-config-error-recovery`; создана от `origin/main` после `git pull origin main`.
- Статус: подтверждено пользователем; реализация завершена, Docker/HTTP/Q2 проверки пройдены. Полный MiniMax-разбор проверяется в связанной задаче.
- Связанный контекст: MiniMax M3.1 Flash реализуется отдельной ранее подтверждённой задачей `message-batching-minimax`; её незакоммиченные изменения сохранены в исходной рабочей копии.

## Проверенная диагностика

- В production на момент проверки активны две записи `AISettings`: `OpenRouter Free` (`openrouter/free`, основная) и `SmertAPI · GPT Sol 5.6` (резервная). MiniMax-конфигурации нет. URL провайдера и имя модели являются редактируемыми текстовыми полями, не enum из двух провайдеров; API уже умеет создать новый профиль и выбрать основной.
- Для конфигураций отсутствует API `DELETE` и кнопка удаления. Поля новой записи по умолчанию всё ещё называют OpenRouter; при отсутствии активной записи `AISettings.get_active()` возвращает не сохранённый объект с этими Django-defaults, поэтому путь «удалить всё» требует явного fail-closed поведения, без отправки запроса на default OpenRouter.
- В указанном групповом чате текущая последняя трассировка со статусом `error` есть у 44 сообщений; иных таких сообщений в production на момент проверки не обнаружено. Из них 21 сообщение уже имеет `RawMessage(processing_state=analyzed, processed=True)`: `evidence_not_in_source` — 16, `context_configuration_changed` — 4, `fact_thread_missing` — 1. Остальные 23 имеют raw-статус `failed`: `provider_response_previously_used` — 17, `invalid_extraction_schema` — 3, `provider_invalid_request` — 2, `provider_overloaded` — 1.
- Ещё 3 сообщения со raw-статусом `failed` имеют последнюю трассировку `warning`; всего 26 raw-failed сообщений в базе, все из указанной группы. Пересечение 23, поэтому объединённая выборка актуальных error/failure кандидатов — 47 сообщений.
- В базе есть 956 исторических `error`-трассировок, но большинство не являются последним состоянием сообщения. Они не должны без разбора повторно применяться или удаляться.
- Веб-маршрут `POST /api/messenger/records/<id>/reanalyze/` уже ставит новую попытку с проверкой team-lead, MFA, аудита и idempotency key. Повтор сохраняет старые трассировки. Текущая очередь не имеет общей безопасной команды для повторной постановки всех актуальных ошибок диалогов.
- Production пока работает на OpenRouter Free; незавершённая MiniMax-реализация из отдельной рабочей копии не включена в production. Массовый повтор до появления настроенной и успешно проверенной основной MiniMax-конфигурации может снова вызвать текущий провайдер.

## Требования

1. Оставить провайдера динамическим: URL, протокол, имя модели и ключ задаются в выбранном профиле; список провайдеров не должен быть захардкожен. Для нового профиля не подставлять OpenRouter URL/model как работающий маршрут. MiniMax использует профиль с её URL/model и штатно зашифрованным ключом Chat API.
2. Добавить удаление AI-профиля в API и интерфейсе. Удалять только после явного действия пользователя и только если нет живого резервирования/операции, которая использует этот профиль. Если профиль основной и остаются активные профили — перед удалением выбрать другой основной или потребовать сначала переключить. Не удалять ProviderUsage, ProviderReservation, AuditEvent или трассировки; ссылки истории отвязывать. API-ключ удалённого профиля должен исчезать вместе с записью.
3. Поддержать состояние «конфигураций нет»: AI-провайдеры выключены, создание нового профиля доступно согласно существующим permissions/MFA, внешние AI-вызовы завершаются понятным `ai_not_configured`. Никакой не сохранённый Django-default или старый резервный профиль не должен незаметно запускать OpenRouter/SmertAPI.
4. Переанализировать текущие сообщения, где либо raw всё ещё `failed`, либо последняя трассировка имеет `status=error`, в разрешённой пользователю области. Объединять выборки без дублей, исключать человеческие `clarification_reply`, активные обработки и дублирующие запросы. Использовать тот же `require_reanalysis`, MFA и аудит, что у штатной команды одного сообщения.
5. Не перезаписывать старые трассировки и не удалять историю ошибок. Результат новой попытки должен заменить текущий видимый статус только после readback. Если повторно не подтверждены доказательства/схема — показывать «Требует проверки» с безопасным объяснением, не автоматически принимать факт и не маскировать его как успех.
6. Повтор выполнять только после того, как MiniMax-подключение настроено пользователем и проверка связи завершилась успешно. Не переключать production AI-маршрут и не вставлять ключи в этом изменении; пользователь сам задаст ключ в панели.
7. Для пакетной операции возвращать детальный итог без текста сообщений и секретов: всего найдено, поставлено, пропущено как уже выполняющееся/недоступное, требует ручной проверки. Повторный запуск не создаёт вторые активные задания для той же исходной попытки.
8. Не создавать unit/component/integration/mock тестовые наборы согласно AGENTS.md. Проверить реальные API и очередь на изолированной Docker-среде; никакой массовый production-повтор в рамках реализации не запускать до готовности MiniMax и отдельного контрольного прохода.

## Планируемые изменения

- `AISettings`/`ProviderReservation`: сделать ссылку резерва nullable с `SET_NULL`; сохранить исторические расходы и резервирования при физическом удалении профиля.
- `AISettings.get_active()` и вызовы моделей: primary выбирается единственным источником активного маршрута; отсутствие primary/профиля ведёт к явному `ai_not_configured`, без model defaults.
- `backend/api/settings_api.py`, `frontend/src/views/SettingsView.vue`: добавить DELETE с серверными проверками, подтверждение удаления и пустое состояние. Оставить произвольные безопасно проверяемые HTTPS URL и текстовые ID моделей.
- `backend/api/messenger_api.py` и `frontend/src/views/MessengerView.vue`: добавить пакетную постановку актуальных ошибочных сообщений выбранной области через текущую проверку доступа/MFA и `schedule_reanalysis`; показать статус результата обработки.
- Миграция сохраняет существующие строки usage/reservation, не удаляет старые записи.

## Критерии готовности

- Пользователь может создать профиль MiniMax с произвольными URL/model/key, выбрать его основным, удалить неиспользуемые профили OpenRouter/SmertAPI и при необходимости оставить ноль конфигураций без скрытого сетевого fallback.
- Попытка удалить профиль с активным резервированием/операцией получает объяснимый конфликт; история использования и аудит остаются доступными после удаления.
- На указанном чате выборка на момент диагностики равна 47 уникальным сообщениям; пакетная команда ставит допустимые сообщения в очередь один раз, применяет права/MFA, а безопасные исключения возвращает в счётчиках. Исторические трассировки сохраняются.
- Никакая повторная AI-обработка не запускается через OpenRouter/SmertAPI после пользовательского переключения на MiniMax.
- Проверки: frontend Docker build с Vue/TypeScript, Django `check`, `makemigrations --check` (`No changes detected`), миграция на временной Docker-БД, `git diff --check`, просмотр backend/qcluster/WAHA логов из изолированного runtime.
- Production config deletion, route switching, bulk replay и deployment выполняются отдельно после пользовательского ввода ключа MiniMax и успешного canary/readback.

## Реализация и выполненная проверка

- DELETE доступен с отдельным delete permission, штатным MFA и блокировкой активного профиля, живых резервов, connection-check и незавершённого пакетного переанализа. Ключи удаляются вместе с профилем, usage/reservation остаются со снятой ссылкой. Ограничения действуют также в Django admin.
- Новый профиль имеет пустые URL/model, состояние без основной модели возвращает `ai_not_configured`. Исторический расход удалённых профилей сохраняется в общих итогах, но не списывается в квоту нового профиля.
- Пакетный API `messenger/reanalyze-errors/` сохраняет снимок целей в AsyncOperation; durable outbox/Q2 ставит до 50 целей за один шаг. Действуют проверки team-lead, MFA, отзыва доступа, текущей версии попытки и идемпотентности. Каждая попытка закреплена за проверенной основной конфигурацией и не вызывает резервные профили.
- Все новые факты пакетного восстановления удерживаются для человеческой проверки перед CRM. Повторно отвергнутые доказательства показываются как «Требует проверки» с сохранённым кодом причины; ошибки доступа/провайдера остаются ошибками.
- Docker: backend/frontend build, новая миграция 0067 на чистой PostgreSQL, `check`, `makemigrations --check` — успешно. Через реальные HTTP проверены пустой список, создание/удаление профиля, сохранение usage/reservation, блокировки активного профиля и живого резерва, отсутствие доступа у постороннего пользователя и отсутствие сетевого вызова без настройки.
- Реальная проверка выключенного MiniMax QA-профиля через Q2 успешна: 219 входных / 3 выходных токена. Пакетная команда через HTTP/Q2 поставила 3 синтетические цели; повтор UUID вернул ту же операцию без дубликатов; новые трассы имеют review-before-delivery и quiet.
- Контрольный синтетический разбор в основной ветке остановился до HTTP модели с `context_tokenizer_unavailable` (0 добавленных provider-запросов, 0 кандидатов, 0 CRM-команд). Полный разбор требует завершения ранее согласованной MiniMax-токенизации/транспорта из отдельной задачи. Production не изменялся.
- Дополнительно через Q2 подтверждены остановка до HTTP при смене конфигурации и отзыве доступа, блокировка удаления профиля с ожидающими разборами, корректный терминальный счётчик без вечного ожидания. HTTP/SQL-проекция проверена для «Требует проверки» и снятия этого состояния после решения по предложениям; неподтверждённый MFA отклоняет пакетную команду.
