# Bugfix: Качество извлечения сделок из WhatsApp и UX чат-ассистента

**Ветка:** `bugfix/chat-quality-and-ux`
**Дата:** 2026-09-26 15:21 MSK

---

## Постановка

При обработке сообщений из WhatsApp и при работе с чат-ассистентом Mazory
обнаружены 5 независимых дефектов:

### D1. LLM копирует сырой текст сообщения в `next_action` и `current_action`

Модель вместо краткого резюме вставляет полный текст входящего сообщения
(включая приветствия «Ассалаумагалейкум…») в поля `next_action` и
`current_action`. Причина — описание полей в `system_prompt_worker` слишком
абстрактное («Что сделано», «Следующий шаг») и не содержит ограничений по
длине или инструкций не копировать исходный текст.

### D2. Сделки создаются с `contract_amount = 0`

В `process_incoming_message_task` нет валидации обязательных полей перед
`Project.objects.create()`. LLM может вернуть `can_create_deal: true` при
`contract_amount: null`, и сделка создастся с суммой 0 ₸.

### D3. HTML-теги (`<br>`) попадают в поля Bitrix24

Если LLM возвращает HTML-теги внутри `current_action` или `next_action`, они
каскадно попадают в COMMENTS и Timeline-комментарии сделки в Bitrix24. Нужна
санитизация перед записью.

### D4. Чат-ассистент возвращает Markdown, но страница его не рендерит

Ответ `AIService.chat_assistant()` содержит Markdown-разметку (`**bold**`,
`- списки`, эмодзи), но `KpiDashboardView.vue` выводит его через
`{{ responseText }}` (Vue text interpolation), которая экранирует все теги.
Результат — пользователь видит сырую разметку.

### D5. Форма чата не блокируется при ожидании ответа

`isGenerating` существует в `useChat.ts`, но **не передаётся** в
`ChatInput.vue`. Кнопка отправки и поле ввода не дизейблятся, нет
loading-индикатора. При 3 быстрых отправках ответ перезаписывается 3 раза.

## Требования

### R1. Улучшить `system_prompt_worker` (D1)

- Описания полей `current_action`, `next_action` должны явно запрещать
  копирование сырого текста и ограничивать длину до 120 символов.
- Добавить правило: если сообщение содержит отчёт по нескольким объектам,
  извлечь **один** объект с наибольшей коммерческой значимостью или вернуть
  `is_deal_fact: false`.
- Добавить в промпт явное требование: «Никогда не копируй текст сообщения
  целиком ни в одно поле. Каждое поле — краткий факт.»

### R2. Валидация обязательных полей перед созданием сделки (D2)

- Сделка не создаётся, если `contract_amount` отсутствует, `null`, `0` или
  отрицательный.
- Сделка не создаётся, если `object_name` пустой или состоит только из
  стоп-слов (приветствия, служебные фразы).
- При провале валидации: логировать `logger.info` с причиной, не создавать
  `Project`, не ставить задачу в Bitrix24.

### R3. Санитизация HTML в полях перед отправкой в Bitrix24 (D3)

- Перед записью `current_action` и `next_action` в `fields` / `update_fields`
  словаря Bitrix24 — strip HTML-тегов (`<br>`, `<b>`, и т.д.).
- HTML допустим только в поле `COMMENTS`, где он ожидается Bitrix24.

### R4. Рендеринг Markdown в ответе чат-ассистента (D4)

- Установить библиотеку `marked` (lightweight Markdown → HTML parser).
- В `KpiDashboardView.vue` заменить `{{ responseText }}` на `v-html` с
  sanitized Markdown-рендером через `marked`.
- Sanitize output через `DOMPurify` для защиты от XSS.

### R5. Loading-state и защита от повторных отправок (D5)

- Передать `isGenerating` из `useChat()` в `ChatInput.vue` как prop.
- При `isGenerating === true`:
  - Дизейблить кнопку отправки и поле ввода.
  - Показать spinning-индикатор вместо иконки `ArrowUp`.
  - Скрыть suggestion chips.
- Показать skeleton/pulse-текст в зоне `responseText` во время ожидания.
- Гарантировать, что повторный submit при `isGenerating === true` игнорируется.
