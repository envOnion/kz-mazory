## Постановка и подтверждённые результаты диагностики

1. Пользователь видит отдельные темы для отдельных сообщений, например #877 «Принято», вместо содержательной переписки.
2. Пользователь не видит результатов сопоставления импортированных сообщений с CRM Bitrix.
3. Пользователь ожидает автоматически получаемый персональный MCP токен в кабинете после входа и возможность проверки фактов через внешний LLM.

Срез серверных данных от 7 октября 2026 года:

- 502 активные темы: 175 open, 323 ready, 4 unknown. Из них 448 (89,2%) содержат одну реплику; у 492 отсутствует summary. Это подтверждает проблему качества группировки, хотя отдельные сообщения могут быть самостоятельными темами.
- #877: version=1, state=ready, topic=«Принято», summary пустое; единственный источник — RawMessage #218 (waha), автор не указан. Перед ним #217 — отчёт длиной 2187 символов за две минуты до ответа.
- У #877 metadata фиксирует 10 включённых сообщений и 7873 входных токена, но earlier_messages_context=[] и earlier_messages_count=0. Восстановление сохранённого запроса даёт context_snapshot_mismatch.
- У 654 из 671 успешной пакетной трассировки metadata сообщает непустой контекст, а сохранённый контекст пуст. В pipeline.extract_message target_traces.update загружает второй ORM-экземпляр основной трассировки; финальный member.save перезаписывает поля прежними значениями. Нельзя на этом основании утверждать, что модель не получила контекст: первоначальный payload формируется с ним.
- Настроен пакет из одной цели, вход 8192 и выход 4096 токенов. Выбор соседних сообщений использует расстояние по ID; при совместной истории WAHA/TXT это не равнозначно близости по исходному времени.
- PACKET_PROMPT и текущий контракт допускают самостоятельную ready-тему информационной реплики; нет достаточного требования связывать зависимый ответ с его содержательным вопросом/отчётом. summary и thread_id необязательны.
- Ожидают review 107 фактов: 52 project (все crm_match_state=disabled), 20 payment и 35 commitment (все not_requested). Для ряда платежей/обязательств отсутствуют object_name и company_name; поиск для таких фактов сейчас не планируется.
- 63 CRM задачи завершились статусом done, но результаты кандидатов — disabled. Завершение задачи очереди не означает выполненный поиск Bitrix. Последний сохранённый disabled — 04:58 UTC; текущие настройки обновлены в 08:21 UTC и crm_matching_enabled=True. Старые кандидаты автоматически не перепроверялись.
- Каталог: state=error, error_code=crm_import_disabled, imported_count=0; Project в базе — 0. Bitrix is_active=True, crm_matching_enabled=True, auto_import_deals=False, hourly_sync_enabled=False.
- Файловый запуск #10: 701 сообщение, 672 текстовые цели; 573 проанализированы, 99 ошибок; 176 из проанализированных — insufficient_data. Полное качество обработки истории не подтверждено.
- MCP реализован на /api/mcp/fact-review/: list_candidates, get_candidate_details, get_candidate_context, list_projects, review_candidate. Решения approve/reject/match/match_crm требуют reason; changes позволяют исправить значение при подтверждении.
- McpToken в базе — 0. VerifyCodeView не создаёт MCP токен; frontend не использует /mcp/tokens/. Текущий POST выдаёт секрет один раз; GET возвращает только метаданные, поскольку в БД хранится только SHA-256.
- MCP контекст выбирает первый ThreadMessage исходного сообщения, хотя у одного отчёта бывает несколько тематических связей. Это может показать контекст другого факта. В общем REST authentication MCP токен сейчас принимается также вне MCP endpoint.

## Требования

### Временная недоступность AI

- До восстановления AI не запускать контрольные LLM запросы и массовый переанализ рабочего чата. Работа над кодом после утверждения спецификации, сборка, миграционные проверки, тесты с подменой провайдера, MCP и независимые проверки CRM не требуют работающего AI.
- Недоступность провайдера не означает отсутствие фактов или завершение анализа: показывать явное состояние/причину, сохранять прежние темы, факты и контекст. Ошибочный ответ или транспортный сбой не заменяются результатом facts=[].
- Сохранить задания и покрытие истории для дальнейшего продолжения; использовать существующую ограниченную политику повторов. Не запускать массовые повторы для обхода недоступности, не переключать модель или провайдера без отдельного основания.
- Доступность самого MCP проверяется обычным протокольным клиентом без вызова LLM; end-to-end работа внешнего LLM и качество семантической группировки требуют отдельной проверки после восстановления AI.
- После восстановления провайдера и утверждения спецификации сначала выполнить небольшой контрольный анализ, затем восстановительный проход. До этих проверок качество группировки и повторного извлечения рабочего чата считать непроверенным; отразить это в этой спецификации и результате PR.

### Содержательные диалоги и достоверный контекст

- Сохранить полный буквальный снимок контекста основной и остальных целей пакета. Счётчики, metadata, snapshot hash и содержимое должны соответствовать фактически отправленному запросу; завершение обработки и повтор не должны стирать контекст.
- При смешанной истории WAHA/TXT выбирать ближайшие реплики по исходному времени, с явным порядком при одинаковой временной точности. ID используется как стабильный дополнительный порядок, а не мера временной близости. Сохранить ограничения токенов, лимиты повторов и проверки источника.
- В приоритетном контексте оставлять сообщение, на которое дан ответ, и существенные оригиналы существующей темы; при нехватке бюджета явно отражать недостаток основания. Не вытеснять предшествующий отчёт списком однословных тем.
- LLM классифицирует смысловую связь. Зависимые «Принято», «Ок», ответы о сроке/сумме продолжают соответствующий вопрос, отчёт или объект, если источники подтверждают связь. Название описывает предмет обсуждения, summary кратко объясняет его, messages содержат связанные оригиналы.
- Новая тема создаётся для самостоятельного предмета; совпадение одного слова или близость во времени сами по себе не являются доказательством объединения. Общая благодарность не подтверждает выполнение обязательства.
- Проверять согласованность использования known_threads, оригиналов, thread_id и версий. Повторная классификация связанных оригиналов не должна создавать параллельные активные дубли этой темы.
- Не восстанавливать утраченный старый AI снимок под видом фактически использованного контекста. Старые трассировки с расхождением помечать/показывать как неполные; новые попытки сохраняют корректный снимок.
- Продолжение темы без новых фактов сохраняет её прежние pending предложения. Заменяются предложения только повторно анализируемых оригиналов и новых доказательств, а не все предложения темы из-за ответа «Принято».
- Автор из TXT показывается при наличии достоверной связи с оригиналом. Не угадывать отсутствующий WAHA номер или автора.

### Сопоставление Bitrix

- Отделить разрешённое чтение каталога для проверки фактов от auto_import_deals и исходящих операций. При crm_matching_enabled=True пользователь с нужной ролью может фоново загрузить каталог, даже если auto_import_deals=False.
- Показать отдельно текущее состояние подключения/поиска CRM, состояние загрузки каталога и сохранённое состояние поиска конкретного факта. Ошибка загрузки каталога не является результатом сопоставления.
- Добавить доступное пользователю повторное сопоставление pending фактов после включения CRM: disabled/not_requested/error с проверкой роли, идемпотентностью и увеличением crm_match_revision. Определённые matched/ambiguous результаты сохраняются до явного повторного запроса.
- Проверять project, payment и commitment с доказуемыми признаками объекта/компании либо уже связанным проектом. Перенос названия из контекста требует буквальной identity-цитаты.
- Для общей реплики без бизнес-факта внешнее сопоставление не требуется. Общие обязательства команды могут не иметь проекта. Если коммерческий факт требует объект, но связь не установлена, показывать причину; не выдавать отсутствие поиска за отсутствие совпадений CRM.
- Никакие изменения каталога/повторы поиска не должны включать автоматическое принятие фактов, создание сделок или запись сообщений/сумм в Bitrix.
- Все внешние чтения Bitrix и LLM выполняются через Outbox/Django Q2, с существующей областью команды и бюджетами запросов.

### MCP токен в кабинете

- После успешного OTP входа обеспечить один активный персональный MCP токен для пользователя. Повторный вход не меняет работающий токен. Для уже вошедших пользователей предусмотреть явное получение токена в том же разделе кабинета.
- В разделе безопасности профиля показать URL MCP, способ передачи Authorization: Bearer, токен с «Показать/Скопировать», даты создания/использования, управление перевыпуском и отзывом. URL: https://ai.mazory.best/api/mcp/fact-review/ в production; в коде выводить из настроенного API URL.
- Токен доступен повторно после обновления страницы и входа с другого устройства. Для этого хранить его зашифрованным через Fernet; использовать существующий параметр MFA_ENCRYPTION_KEY и dev fallback из SECRET_KEY по принятому в проекте механизму. SHA-256 остаётся индексом проверки. Открытый секрет не записывается в логи, localStorage, аналитику и общие профильные ответы.
- Выдача/показ/перевыпуск выполняются только для текущего пользователя через JWT endpoint. Возвращать Cache-Control: no-store. Токен внешнего агента не позволяет получить или создать другие персональные токены и не принимается как авторизация общего REST API.
- Сохранить ранее выданные external токены и их ручное управление; хешированный секрет существующего токена восстановить невозможно. Активный portal токен создаётся отдельно.
- Токен даёт доступ к MCP проверки фактов в пределах текущих ролей и объектов пользователя. Права проверяются при каждом запросе; отключение пользователя/отзыв доступа прекращает работу токена. Перевыпуск прекращает работу предыдущего токена.
- Отзыв не должен незаметно отменяться при обновлении профиля: показать отсутствие активного токена и явное действие получения нового. Новый OTP вход может обеспечить новый токен, как требуется пользователем.
- При недоступном шифровании показать конкретную ошибку доступа MCP; не хранить секрет открытым и не ломать обычный вход пользователя.

## Критерии готовности и проверки

- Одноцелевая и многоцелевая пакетные попытки с непустым контекстом сохраняют его во всех трассировках. _restore_request воспроизводит hash исходного payload после чтения JSONB; завершение попытки не стирает контекст.
- Отчёт → «Принято» находится в одной содержательной теме с оригиналами, summary и связью ответа, если связь подтверждена; реплика о другом объекте не сливается из-за близости. Два последовательных прохода не умножают активные темы/факты.
- Тест смешанной истории с несмежными ID подтверждает временную близость. Конфликт версий, нехватка контекста и ошибка модели оставляют прежние результаты и имеют явную причину.
- При crm_matching_enabled=True и auto_import_deals=False загрузка read-only каталога выполняется; при отключении чтения/невалидном подключении показана отдельная причина.
- Старые disabled факты перепроверяются; результаты становятся matched/ambiguous/not_found/error по реальному ответу CRM. Платежи/обязательства с доказанным объектом попадают в тот же путь. Безобъектные обязательства не требуют выдуманного проекта.
- Первый OTP вход создаёт один portal токен; повторный вход/две одновременные операции не создают активных дублей. Пользователь может скопировать токен после перезагрузки и на другом устройстве.
- БД хранит хеш и шифротекст, открытого токена в логах/общем профиле/localStorage нет. JWT другого пользователя и MCP токен не могут получить секрет. Отозванный/перевыпущенный токен перестаёт работать.
- Реальный MCP клиент с данными кабинета проходит initialize, tools/list и разрешённое чтение. API тесты подтверждают approve с исправлениями и reason, reject, match_crm, защиту ролей и конфликтов. Бизнес-факты рабочего чата не подтверждаются тестами автоматически.
- MCP контекст отчёта с несколькими темами относится к выбранному факту; доступны страницы переписки WAHA/TXT и сохранённого AI снимка с проверкой доступа.
- Полный восстановительный проход содержит честные числа total/processed/errors/insufficient_data и CRM состояний. Результат не признаётся готовым только по состоянию done очереди или по наличию тем.
- Тесты временной недоступности AI подтверждают сохранение прежних результатов, явную причину ожидания/ошибки, ограниченные повторы и возможность последующего продолжения. Успех тестов с подменой провайдера не подтверждает качество реального семантического анализа.
